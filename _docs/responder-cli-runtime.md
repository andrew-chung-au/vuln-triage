## What the runtime is

`RESPONDER_MODE=real` with `RESPONDER_RUNTIME=cli` (the default) runs **one headless `claude -p` per alert** in the fresh checkout, on the owner's own Claude login. No API key. The agent only commits locally. After the run the **runner** checks the commits, pushes `responder/<fingerprint>` and opens the pull request. This is the shape of the coursework's `04-order-tracker` (webhook returns at once, headless `claude -p`, a fixed allow list and a deny list because a headless run cannot ask, the agent never pushes, its own process group and a time limit, the token kept out of the agent), with the push and the PR moved into the runner.

```
webhook -> 202 -> background run:
  clone -> make install (runner, no secrets) -> record base sha + .git/config digest
  -> claude -p (agent: reads, edits, make test, git add/commit)   [own process group, time limit]
  -> kill the process tree (group, then VT_RUN_MARKER)
  -> diff gate (publisher.py) -> git push (token here only) -> REST: open PR -> S4 read-back
  -> remove the checkout -> clean up a branch this run created if the run failed
```

Files: `responder/vt_responder/cli_session.py` (the session and the preflight), `cli_rules.py` (rules generated from `policy.py`), `publisher.py` (diff gate, push, PR), `envscrub.py` (`cli_env`), `prompt.py` (`CLI_SYSTEM_PROMPT`). Tests drive a fake `claude` (`responder/tests/fake_claude.py`).

## The flags used, and the source of each

Source key: **help** = `claude --help` / `claude auth --help` on 2.1.311 in this sandbox; **headless** = code.claude.com/docs/en/headless; **cli-ref** = code.claude.com/docs/en/cli-reference; **perm** = code.claude.com/docs/en/permissions; **auth** = code.claude.com/docs/en/authentication; **errors** = code.claude.com/docs/en/errors.

| Flag or command | What it does here | Source |
|---|---|---|

| `--model <model>` | the model from `RESPONDER_MODEL` | help |

Flags deliberately **not** used: `--bare` ("never reads OAuth credentials or the system keychain", so it cannot use a login; headless, help), `--dangerously-skip-permissions` and any `bypassPermissions`/`acceptEdits` mode, `--max-budget-usd` (a dollar cap means nothing on a plan; the turn and time limits bound the run instead), `--permission-prompts none` (needs 2.1.259 or later; in a `-p` run with no host those requests are denied anyway, the flag only tells Claude not to retry).

Preflight (`cli_session.preflight`, run once by `create_app` before the first alert): the binary is on `PATH`; `claude --help` lists every flag in `REQUIRED_HELP_FLAGS`; `claude auth status` exits 0; `authMethod` is `claude.ai` or `oauth_token`. Anything else (including `api_key`, `api_key_helper`, `third_party`) refuses to start with a message naming the cause, because those methods may bill something other than the plan. The preflight runs with the **same scrubbed environment as a run** (`cli_env`), so an `ANTHROPIC_API_KEY` set on the responder cannot make it look logged in.

## Credentials and the environment (auth page)

Precedence when several credentials exist (auth): cloud-provider variables, then `ANTHROPIC_AUTH_TOKEN`, then `ANTHROPIC_API_KEY` ("In non-interactive mode (`-p`), the key is always used when present"), then `apiKeyHelper`, then `CLAUDE_CODE_OAUTH_TOKEN`, then profiles, then the saved subscription login. So an API key or auth token in the environment **overrides the login and bills the API**, which is why `cli_env` removes them.

The saved login on Linux is `~/.claude/.credentials.json` under `HOME`, or under `CLAUDE_CONFIG_DIR` when that is set (auth). The CLI's environment is therefore built from scratch (`envscrub.cli_env`): the existing allowlist (`PATH`, `HOME`, `LANG`, proxy and CA names, ...) plus `CLAUDE_CONFIG_DIR` and `CLAUDE_CODE_OAUTH_TOKEN` (the login variables), the run marker and a git identity. `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_BASE_URL`, profile and federation variables, the Bedrock/Vertex/Foundry switches, `GH_TOKEN`, `GITHUB_TOKEN` are removed even if someone adds them to an allowlist (`CLI_FORBIDDEN`). No responder secret and no `GIT_CONFIG_*` credential is in it. `VERIFY:` the macOS login is in the Keychain (auth), which `HOME` alone does not reach from every context; the target host is Linux.

## Tool rules (perm page) and what they cannot do

Generated by `cli_rules.build_rules()` from `policy.py`'s constants (writable roots, protected components and suffixes, lockfiles, make targets, git subcommands). Semantics relied on, from **perm**:

* Evaluation order is deny, then ask, then allow, and "the first match in that order determines the outcome": **a deny always wins over a more specific allow**.
* `Bash(git diff *)` is a prefix rule (the space before `*` matters; a trailing ` *` also matches the bare command). Compound commands are split on `&&`, `||`, `;`, `|`, `|&`, `&` and newlines and each part must match an allow rule; a deny rule applies if **any** part matches, including inside `$(...)`.
* `Edit(backend/**)` as an allow rule is anchored at the working directory; `Edit(**/.github/**)` matches at any depth. "Claude Code checks file permissions against `Edit(path)` and `Read(path)` rules only": a `Write(...)`, `Glob(...)` or `MultiEdit(...)` path rule is accepted but never matches, so the generated rules use only `Edit(...)` and `Read(...)`.
* `Read(!**/.env.example)` after `Read(**/.env*)` carves the example file back out ("a `!` rule listed first carves nothing out").
* Reads inside the working directory need no rule under `dontAsk`; a bare `Read` allow would also reach files outside the checkout (the login under `HOME`), so it is not granted.

Generated lists (see the output of `build_rules()`; the test file `responder/tests/test_cli_rules.py` has one test per refused case against them):

* **Allowed**: `Edit(backend/**)`, `Edit(tests/**)`, `Edit(frontend/**)`, `Edit(responder/**)`; `Bash(make backend-test)`, `Bash(make responder-test)`, `Bash(make test)`; `Bash(git status *)`, `Bash(git diff *)`, `Bash(git log *)`, `Bash(git add backend/*)` (and `tests/`, `frontend/`, `responder/`), `Bash(git commit -m '*')` and its double-quoted form (they replace the earlier `-m *`). Denied on top, because a prefix rule alone lets them through (QA findings 2 and round 2): for `git status|diff|log`, `--output`, `--no-index`, `--ext-diff`, `--textconv`, `--orderfile`, `-O` (as substrings `--ou`, `--no-i`, `--ext`, `--text`, `--or`, `-O`, plus every prefix of three characters or more as a whole argument) and any quote, backslash, `$`, `{` or `}`; for `git add`, any `$`, `{` or `}` and any flag (`--` included), `.`, `..`, an absolute path, a quote, backslash, tab or `*` (escaped `\*` in a rule), and a protected name (`.env*`, `Dockerfile*`, `compose*.yaml|yml`, Terraform suffixes, lockfiles, protected directories, `responder/vt_responder/`); for `git add`, a space after the path (one path per command). **`git commit` is a positive match, not a list of bad flags** (three QA rounds each found a spelling a list missed): it is allowed in exactly one shape, `git commit -m "<text>"` or `git commit -m '<text>'`, because the allow rule fixes the start (`-m` and an opening quote) and the end (the closing quote), and the deny rules make `<text>` one shell word: a third quote of the same kind (`*"*"*"*`, `*'*'*'*`) is refused, as are a backslash, `$`, `{`, `}`, tab, VT, FF, CR, a text starting with `-`, a backtick and any `& ( ) ; < > |` (checked as separators or redirections by the model). A rule is a glob and cannot state a character set, so the rules express the shape, not an allowed alphabet; the stricter, tokenising check is `ToolPolicy`, and `test_cli_rules_differential.py` asserts that over thousands of generated commands the rules never allow a `git add` or `git commit` that `ToolPolicy` refuses (the one carve-out: leading and trailing space, tab and newline are trimmed). Ordinary messages such as `Fix: handle None in notifier`, `Don't drop failed jobs` and `fix #123: retry the job` are allowed; `prompt.py` tells the agent the rules (no double quote inside a double-quoted message, so at most two apostrophes).
* **Denied**: `WebFetch`, `WebSearch`; `Bash(git push *)`, `gh`, `curl`, `wget`, `ssh`, `scp`, `sudo`, `pip`, `uv`, `uvx`, `npm`, `npx`, `node`, `pytest`, `python`, `python3`, `git config|remote|checkout|switch|branch|reset|rebase|merge|tag|fetch|pull|clone`, `make *install*`, anything containing `merge`; `Edit` on every protected component (`.github`, `terraform`, `infra`, `deploy`, `ci`, `.git`, `.claude`, ...), on `*.tf`/`*.tfvars`/..., `.env*`, `Dockerfile*`, `compose*.y*ml`, the lockfiles, and `responder/vt_responder/**`; `Read` on `.env*` except `.env.example`.

What a CLI rule **cannot express**, so the runner's diff gate is the control (see the next section):

1. The arguments of `git add` and `git commit` can be constrained only by prefix and substring patterns (perm: argument-constraining Bash rules are fragile). The generated rules do this best effort (above) and `ToolPolicy` is stricter still; left to the diff gate alone: a protected name in another case, `?`, `[` and `]` globs in a `git add` path (a `?` deny rule could be read by the CLI as a wildcard and refuse every add, so it is not generated), a symlink, and a path the patterns do not know. Two syntax assumptions are `VERIFY:` items: that `\*` and `\\` in a rule are a literal asterisk and backslash (if not, those deny rules are inert), and that `Bash(git commit -m '*')` matches the command text with its quotes (if the CLI strips quotes, the agent cannot commit and the run fails, which is safe but useless). Whitespace: bash splits words on a tab, which the space-based `git commit` patterns do not see, so tab, vertical tab, form feed and carriage return are refused in every argument of `git status|diff|log|add|commit` (QA round 4); Unicode spaces are not word separators in bash and are not refused. Shell expansion: the rules match the text the agent wrote, and bash expands it afterwards, so `--${u}output=x` would run as `--output=x`. The generated rules therefore refuse `$`, `{` and `}` anywhere in a `git status|diff|log|add|commit` command (a message containing them is refused too), which closes the forms QA found (`${u}`, `$HOME`, `{a,b}`). `VERIFY:` whether the real CLI matches a rule against the raw or the expanded text; if it matches the expanded text these refusals are redundant, if the raw text they are what stops it. Other expansions that need none of those characters (`~`, and the `?`, `[`, `]` globs) are not refused by the rules. The tests check these refusals against `cli_rules.evaluate`, this repository's model, not against the real CLI.
2. A program in another spelling: `Bash(curl *)` does not match `/usr/bin/curl`, `sh -c 'curl ...'`, `env curl`; `Bash(git push *)` does not match `git -C . push` or `git -c ... push` (perm, table of "what a rule doesn't match"). Those are not allowed either, so `dontAsk` denies them, but the deny list is not a boundary.
3. Anything the agent's own code does: a test or `conftest.py` that `make test` runs can open sockets, read files outside the checkout, or run `git push` with no credential to push with. No rule sees inside it.
4. Case-insensitive paths: the rules are case-sensitive globs; the gate is case-insensitive.
5. The read-only command set: `dontAsk` still runs it without a rule (headless). `VERIFY:` whether it can read outside the checkout (for example `cat ~/.claude/.credentials.json`); assume it can (this is the accepted login-under-`HOME` limit in `_docs/responder-security-limits.md`).

`cli_rules.evaluate` is **this repository's model** of those semantics, used only by the tests. `VERIFY:` that the real CLI agrees with it for every refused case in `test_cli_rules.py`; the first live run should try a few (a `git push`, an `Edit` of `.github/x`, a `curl`) and read the denials in the output.

## The runner-side diff gate (`publisher.py`), independent of the CLI

After the run, and after the process tree is killed, before any push. A refusal is a failed run with a short reason; nothing is pushed.

| Reason | Refused when |
|---|---|
| `git_config_modified` | `.git/config` differs from its digest right after the clone, checked at the start and again right before the push (it could point the push, with the token, elsewhere). This digest alone is NOT what keeps the push on the right repository: `.git/commondir` made git read another directory's config (found by QA), which is why the next row and the `GIT_DIR` paragraph below exist |
| `git_dir_unexpected` | `.git` is a symlink or not a directory, or holds `commondir`, `gitdir`, `config.worktree`, `info/grafts`, `objects/info/alternates` or `objects/info/http-alternates`, or `.git/config` is not a plain file |
| `no_commits` | the head is still the cloned head although the agent said FIXED |
| `base_not_cloned_head` | the new head does not descend from the cloned head |
| `merge_commit`, `too_many_commits` | any merge commit; more than `RESPONDER_MAX_COMMITS` (default 3) |
| `diff_path_<code>` | a changed file is outside the writable roots, or on `.github/`, infrastructure/Terraform/CI/devcontainer paths, an `.env*` file, a lockfile, or `responder/vt_responder/` (codes from `ToolPolicy.check_publish_path`: `path_not_allowed`, `github_dir`, `infrastructure_path`, `env_file`, `lockfile`, `guard_module`, `path_outside_checkout`); deleted files too |
| `diff_symlink`, `diff_submodule`, `diff_type_change`, `diff_mode_unexpected`, `diff_mode_changed`, `diff_status_unexpected`, `diff_path_odd_name` | a symlink or submodule (a gitlink; listed with `--ignore-submodules=none`, so an untracked `.gitmodules` cannot hide it), a file changing type, a new executable, a mode change, a rename/copy status, a control character in a path |
| `diff_empty`, `diff_too_many_files` | a commit that changes nothing; more than 40 files |
| `diff_path_too_long` | a changed path over 200 characters (`diff_path_odd_name` also covers any character outside `A-Za-z0-9._/+=,~-`: the path goes into the pull request body) |
| `diff_check_failed` | git failed while checking (never a push) |
| `push_failed`, `pull_request_create_failed` | the push or the REST call failed; a branch this run created is removed (S1) |

Every runner git call (gate, squash, push) sets `GIT_DIR` and `GIT_COMMON_DIR` to the checkout's own `.git`, so a `commondir` or `gitdir:` file cannot move where git reads config, refs and objects (tested against a planted `commondir`, absolute and relative; the explicit variables defeat it even with the refusal bypassed). The clone (`checkout.py`) also ignores the global and system config. **Residual, not closed:** (R1) a process that survived the group and marker kill (`env -i`, `setsid`; the kill is best effort) can edit `.git/config` between the second digest check and the push; (R2) the gate reads objects, refs and config from a repository the agent's code could write to, and the refusals are a list of things thought of (loose-object rewrites under the same name are one that was not examined); (R4) the real CLI may not match `cli_rules.evaluate`. The runner's git calls switch hooks and fsmonitor off (`-c core.hooksPath=/dev/null -c core.fsmonitor=false`), read objects without `refs/replace` (`--no-replace-objects`), ignore the global and system git config (`GIT_CONFIG_GLOBAL=/dev/null`, `GIT_CONFIG_NOSYSTEM=1`: the agent runs with the owner's real `HOME` and could have written `~/.gitconfig`), use `--no-ext-diff --no-textconv`, build ONE commit (`git commit-tree` of the checked head's tree on the cloned head, the runner's identity, the PR title as message) so the agent's own commits are never pushed, push that commit as `<sha>:refs/heads/responder/<fp>` to an explicit `https://github.com/<repo>.git` URL (not a remote name from `.git/config`), never force, and pass the token (`git_auth_env`) to that one call. The PR title and body are composed by the runner from the validated fingerprint and finding id and the checked file list; the agent's one-line summary is redacted (`envscrub.redact`), cut to 300 characters, stripped of backticks and put in a code block, and nothing from the API or an advisory is read into it.

## Failure handling (the `reason` in `run_failed`)

`cli_exit_nonzero` (a non-zero exit is never a success, whatever the JSON says), `output_too_large` (stdout or stderr over 5 MB, checked while the CLI runs and after; a `RESULT:` line inside a code fence is not the verdict), `plan_usage_limit`, `max_turns`, `output_unparseable`, `result_line_missing`, `agent_cli_error` (`is_error` or a `subtype` other than `success`), `agent_escalated` (`RESULT: ESCALATE`), `agent_timeout` (the wall-clock limit: the CLI's process group gets SIGKILL, then the runner's marker kill), plus the diff-gate reasons above, `checkout_failed`, `install_failed`. Each is followed by the S1 branch cleanup rule and the checkout removal. To make a failed run diagnosable, `run_failed` also carries an `explanation` field for `agent_escalated` (the text after `RESULT: ESCALATE`), and for `result_line_missing`, `agent_cli_error` and `cli_exit_nonzero` (the last characters of the final `result` message on stdout, whitespace collapsed). It is untrusted agent text: non-printable characters are removed, the session redacts the WHOLE sanitised text first (`envscrub.redacted_window`: the configured secrets and their base64 forms, every occurrence, over the whole text, which the 5 MB output limit already bounds) and only then cuts the window of at most 800 characters (the start of the `RESULT:` text, or the end of the final message; 400 for a denied call's command or path), so a secret the window edge would have bisected is replaced whole and no fragment of it reaches any sink, however many copies of it the window holds (redaction can shrink the text, so the window is counted on the redacted text). The runner redacts again (defence in depth) and then keeps the first 500 (`agent_escalated`) or last 500 (the other reasons) characters, counted in characters not bytes; the log line JSON-encodes it. The same order applies to the `no_change` explanation, to each `denied_calls` entry (cut to 200), and to the summary that reaches the pull request body (redacted, then cut to 300). The SDK runtime's `no_change` explanation follows the same order. The session gets the secrets from `create_app` (`CliSession(secrets=...)`; `build_default_session(secrets=...)` for the SDK). **When a verdict carries no explanation:** if `RESULT: ESCALATE` has no text after it (nothing, whitespace, or only control characters) or fewer than 20 characters, and for `RESULT: FALSE_POSITIVE` with no text, the explanation is instead the last 500 characters of the final message (the verdict line included), redacted first by the same path, so the owner can read what the agent said. A `RESULT:` line inside a code fence is not a verdict (the run is `result_line_missing` and the tail is logged); text after the verdict line is not part of its explanation unless the fallback applies. The text of a `plan_usage_limit` or `max_turns` run is never logged. Residual risk: redaction is exact-match on the configured secrets (API token, webhook secret, GitHub token and their base64 forms); it does not catch other token-shaped strings the agent read elsewhere, and a secret the agent split with control characters or newlines becomes separated by spaces in the tail and stays unredacted. Every `run_failed` whose output parsed (`agent_escalated`, `result_line_missing`, `agent_cli_error`, `cli_exit_nonzero`, `max_turns`, `plan_usage_limit` when the JSON parsed) also carries `denied_calls`: at most 5 strings, from the result's `permission_denials`, each `"<tool_name>: <command or path>"` (the tool name is a validated short token; the value is `tool_input.command` for Bash, else `file_path` or `path`; any other `tool_input` field, file content included, is never read). Same discipline as the explanation: printable characters only, whitespace collapsed, a 400 character window per call, the runner redacts the whole entry first and only then keeps the first 200 characters; a missing or malformed field logs no key; a successful run logs none. This is how a refused `git commit` becomes visible (what the agent typed). Stderr, the environment and the raw output are never logged, and the other reasons (`plan_usage_limit`, `max_turns`, `output_unparseable`, `output_too_large`, timeouts) carry no agent text. `RESULT: FALSE_POSITIVE` pushes nothing and logs the explanation (US-15). There is no dollar budget on a plan; the turn limit and the time limit bound a run.

How a plan usage limit surfaces is **not established**. The errors page lists the messages ("You've hit your session limit", "...weekly limit", "...Opus limit", "...Sonnet limit", "Request rejected (429)", and that temporary 429s are retried automatically with backoff, up to 10 attempts by default) but, in the part read, neither the exit code nor the JSON shape of a headless run that hits one. The code treats a non-zero exit **or** `is_error` as a failed run and labels it `plan_usage_limit` when the output matches `hit your .. limit`, `usage limit`, `rate limit` or `credit balance`. `VERIFY:` the real wording, exit code and JSON on the owner's Pro plan; a retried 429 can also make a run slow, which the time limit then ends.
