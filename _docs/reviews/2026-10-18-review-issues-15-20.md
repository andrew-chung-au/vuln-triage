## Errors, with proposed fixes

### 1. High: the push check will fail on the first push

**What:** `_docs/agent-kit/environments/local-sandbox/pre-push` runs `make -C <project> install verify` in a throwaway container, but only if the Makefile has an `install:` target (line 45). Otherwise it runs plain `verify`. The default image is `python:3.12` (line 29). Since `e3de014`, `TEST_CMD="make test"` → `npm --prefix frontend test` → `vitest run`. In that container:
- the Makefile has no `install` target, only `frontend-install`, so `npm ci` never runs and `node_modules/` is missing;
- `python:3.12` has no `node`/`npm` anyway.

`verify.sh` treats a failed `TEST_CMD` as `FAIL` (lines 22–26), so the push check blocks the push. The same thing happens in any fresh checkout, including this container, before `make frontend-install`. QA never saw it because `node_modules/` was already installed for every run.

**Proposed fix** (needs your approval; `Makefile` is protected and the push check is on your machine):
- Add the kit's conventional target: `install: frontend-install ## Install all dependencies`, and change the AGENTS.md Install line to `make install`.
- Point the push check at an image that has Node 24 plus git, make and python3. For example, set `AGENT_PUSH_CHECK_IMAGE=node:24.22.0-bookworm` (the full Debian image comes with git, make and python3). VERIFY: that this tag exists and has those tools. When #24 adds the uv backend, the image also needs uv. At that point, build a small local image (Node 24.22.0 + Python 3.12 + uv 0.13.1) and use it for the push check.
- Optional: make `frontend-test` fail with a clear message ("run `make install` first") when `frontend/node_modules` is missing, instead of `vitest: not found`.
- Add a Project gotcha to AGENTS.md: "`make verify` needs `make install` first; the push check needs an image with Node."

Before pushing for real, you can check the plan with `AGENT_PUSH_CHECK_PLAN=1` in the clean clone.

### 2. Medium: the built container breaks #20's refused cases (`corepack enable`, unpinned nvm)

**What:** #20 refused "`corepack enable`, or adding pnpm/yarn through the node feature" and "any download from an unpinned URL". In the rebuilt container:
- `/usr/local/share/nvm/versions/node/v24.22.0/bin/` has `yarn`, `yarnpkg`, `pnpm` and `pnpx`. All four are corepack shims, created at 11:24 during the rebuild. The feature's `install.sh` always runs `corepack enable` to provide yarn, unless `installYarnUsingApt` is set. `pnpmVersion: "none"` only skips the separate pnpm install. Only `version: "none"` skips the yarn step. So `pnpmVersion: "none"` did not keep pnpm out: corepack provides it.
- nvm `0.40.8` came from `nvmVersion`, which defaults to `"latest"`. It's resolved by `git ls-remote` at build time and fetched as `raw.githubusercontent.com/nvm-sh/nvm/v<ver>/install.sh | bash`, with no checksum. Locking the feature digest doesn't pin this.

QA checked only the added lines of `git diff -- .devcontainer`. Neither problem shows up there.

**Proposed fix** (a `.devcontainer/` change needs your approval and a rebuild):
- Pin nvm in the feature options: `"nvmVersion": "0.40.8"` (VERIFY: the option accepts a full version, matched against the tags).
- For corepack, pick one:
  - (a) Accept it and record it as a known exception on #20. The shims do nothing until someone runs `yarn` or `pnpm`, and the first run downloads from the registry.
  - (b) Add `corepack disable` to `setup.sh` after the feature runs. It's one line, it's easy to undo, and it removes the shims. **Recommended.**
  - (c) Install Node from the nodejs.org tarball with a SHA-256 check instead of the feature. That's the tightest supply chain, but it's more recipe code to maintain.
- Add a runtime refused-case check to future recipe issues: `command -v yarn pnpm` prints nothing.

### 3. Medium (process): QA ran in the build tool with no recorded exception

### 4. Low: the #20 session summary contradicts itself

**Fix:** Rewrite "What changed" and "Files created or modified" to describe the final state, and keep the history in one sentence.

### 5. Low: `frontend-stop` can kill an unrelated process

`Makefile:56-61` runs `kill`, without checking, on whatever PID is in `.scratch/frontend.pid`. If the container restarts or the server crashes, the file stays and the PID can be reused. `frontend-stop` would then signal a process it didn't start, which breaks the AGENTS.md rule "never stop a process you didn't start". `frontend-start` also ends up treating a reused PID as "already running".
**Fix:** Before `kill`, check `ps -o args= -p "$pid" | grep -q 'vite dev'`. If that fails, report "stale PID file, removed" and delete the file without killing anything.

### 6. Low: `frontend/README.md` contradicts the install policy

The README says the make targets "wrap the commands above", but the commands above are `npm i` / `npm run dev`. The targets actually run `npm ci` and the Vite binary directly. Following the README's `npm i` can rewrite `package-lock.json` outside the `--before` resolution and bypass the "ask before adding a dependency" rule.
**Fix:** Change the "Development" block to `make frontend-install` / `make frontend-start` now. Leaving it to #21's README rewrite also works, as long as #21 lists it.

### 7. Low: small leftovers in protected files

- `opencode.json` has had no trailing newline since `4eb0485`. `git diff --check` doesn't catch this.
- `Makefile:2` still says "install/test/run targets will be added when the project is scaffolded".
- The AGENTS.md "Dependencies" line still says "no stack scaffolded yet".

**Fix:** One protected tidy-up commit, after your approval.

## Choices I would not recommend, and the tradeoffs

**A. Bundling unrelated changes into issue commits.** `4eb0485` (#20's recipe commit) also carried a 34-line `opencode.json` permission rewrite. `dc843de` (tool-versions) carried pending AGENTS.md Project-rules edits. You approved both afterwards, so nothing is wrong now. The cost is that one revert ("revert the commit and rebuild", which is #20's stated undo) would also revert the permission changes. Per-issue review also gets noisier. *Recommendation:* the Engineer runs `git diff --cached --stat` before every commit and stops if anything outside the Constraints is staged.

**B. The OpenCode runtime writes approvals into the tracked `opencode.json`.** It dirtied the tree mid-QA, failed `assert-clean`, and forced a second QA run (`352ff95`). Committing the rules each time keeps things moving, but a protected security file then grows through click-throughs instead of review. *Recommendation:* add the read-only rules each role needs to `opencode.json` up front. VERIFY whether OpenCode can save "always allow" choices to an untracked local file instead.

**C. Agents can edit `.devcontainer/`, `.githooks/` and `.github/` without a prompt.** In `opencode.json`, `edit` is `"*": "allow"` with no ask rule for these paths. The pre-commit hook asks only at commit time. `environments.md` lines 50–51 warn that an *uncommitted* `initializeCommand` in the shared folder runs on your machine at the next rebuild. *Recommendation:* add `".devcontainer/**": "ask"`, `".githooks/**": "ask"`, `".github/**": "ask"` and `".vscode/**": "ask"`. The cost is a prompt on the rare legitimate recipe change.

**D. `"make *": "allow"` now covers network installs and arbitrary code.** With the new targets, any agent can run `make frontend-install` (network, `npm ci`) or `make test` (runs project code) without a prompt. This is acceptable because the Makefile is protected and `npm ci` is locked to the lockfile. Cheap hardening: add `frontend/.npmrc` with `ignore-scripts=true`. I checked the lockfile: only `fsevents` has an install script, and it's macOS-only, so nothing breaks today.

**E. Supply-chain guard after the first install.** `--before=2026-10-18` covered only the first resolve. Bun's 24-hour `minimumReleaseAge` in `bunfig.toml` doesn't apply to npm, and #21 deletes that file. The next `npm install <pkg>` has no age guard. *Recommendation:* #21 should choose an npm-side equivalent. VERIFY whether npm 11.19 supports a minimum release age setting; if it doesn't, document `--before=<date>` for every dependency change. Also unverified: no one checked that the 587 locked versions were all published before 2026-10-18. QA flagged this as a risk. All 587 resolve from `registry.npmjs.org`.

**F. `frontend-start` depends on an implicit shell `exec`.** `cd frontend && nohup vite … & echo $! > pid` records the PID of a background subshell. It's vite only because `sh` optimises the last command into an `exec`. QA confirmed it works here, but another `/bin/sh` could record a wrapper PID. *Recommendation:* make the `exec` explicit, e.g. `(cd frontend && exec nohup ./node_modules/.bin/vite …) & echo $!`. The behaviour stays the same and no longer depends on the shell.

**G. Two lockfiles (`bun.lock` + `package-lock.json`).** It's deliberate (#21 removes `bun.lock`), but until then someone running `bun install` gets a different tree. Keep #21 at the front of the queue.

**H. QA's evidence for the first install.** QA said it "could not re-run the first install without a network call", yet it ran `make frontend-install` (`npm ci`), which is a network call. That's not wrong, just inconsistent. The `--before` acceptance rests on the Engineer's word plus the committed lockfile. Small, but it's the kind of gap a cross-tool QA would have questioned.
